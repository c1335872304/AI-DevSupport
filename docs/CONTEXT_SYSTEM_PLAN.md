# PaiSmart 客服上下文系统实施计划

状态：阶段 0–4 的本地候选验收已通过。正式部署环境的接入和放量由发布验收另行确认。参阅[架构契约和阶段验收](02-architecture/CONTEXT_SYSTEM.md)。

客服上下文系统是 PaiSmart 的独立模块。每轮保存用户原话后，它按客户、会话、诊断或工单、具体请求更新续办状态，并在生成前组装上下文。模块有自己的数据契约、持久化、验收和上线门槛。

改造前，MySQL 已保存原始会话，Redis 缓存近期历史及实体，诊断模块已有持久化状态和证据。每轮历史最多取 20 条消息、12,000 字符。旧实体解析在近期历史非空时从历史提取实体，只在历史为空时使用持久化实体。跨窗口基线验证了这个缺口。[旧实体解析](../backend/app/agent/entities.py) · [基线记录](../backend/data/context-system/baseline.json) · [诊断数据模型](../backend/app/db/models.py)

## 模块设计

| 上下文 | 内容 | 使用规则 |
| --- | --- | --- |
| 近期原话 | 最近完整的问答轮次、最新纠正、当前追问 | 解决近期指代。按完整轮次裁剪。 |
| 结构化续办状态 | 请求号、应用、厂商、地域、版本、账期、已尝试步骤和待核验事项 | 按同一客户和业务范围读取。每个关键值保留来源、时间和状态。 |
| 按需回查的历史 | 较早的原话、报错、排障反馈和历史处置 | 遇到明确指代、冲突或缺少关键字段时，读取同一授权范围内少量原文及记录 ID。 |
| 本轮证据 | 已授权文档及引用、工具回执、仍有效的历史证据引用 | 仅在来源、范围和时效都支持时用于回答。确认当前余额、额度或工单状态时重新查证。 |

MySQL 保存原始记录和权威续办状态，Redis 缓存带版本的状态快照。Redis 不可用时从 MySQL 恢复。诊断和工单沿用现有权威业务记录。

实体压缩采用字段级归并。每个字段至少保留值、来源、原始记录 ID、作用范围、更新时间和状态。重复提及合并；明确纠正更新当前值，旧值保留在历史并记录替代关系；无法判定的冲突进入待核验。例如，用户把当前环境从 v1 纠正为 v2 后，后续排障使用 v2。如果工具核实那次历史请求使用 v1，则将历史请求版本与当前环境版本分别保留。用户口述、工具核验、文档规则和摘要各自保留来源与权限。

- [x] 定义客户、会话、诊断或工单、请求、生成之间的作用范围。明确继续原请求、切换请求、另开会话时允许继承的字段。
- [x] 定义用户口述、工具核验、文档规则和模型摘要的可用范围、失效条件以及可以支持的结论。
- [x] 冻结长会话验收集，覆盖跨窗口续办、用户纠正、同账号切换工单、过期证据、缓存失效和跨账号隔离。
- [x] 沿真实入口执行现状基线，记录每轮写入、读取、继承、裁剪和证据使用结果。

**阶段出口**：发布数据契约和逐轮基线。每条失败能定位到保存、读取、范围继承或证据使用。

## 阶段 1 · 持久化续办状态

- [x] 在统一读写接口中复用诊断状态、证据和执行记录，定义普通客服、账单查询和诊断工单需要保留的字段。
- [x] 实现字段级归并、来源记录、纠正和冲突处理。摘要与旧答复中的推断不能写入已核实字段。
- [x] 实现范围切换和继承。同一范围内用近期原话补充已保存状态，应用明确纠正；切换请求时先确定新范围，指代不清时澄清。
- [x] 实现 MySQL 持久化与 Redis 快照一致性。验证旧快照、缓存失效、服务重启和并发纠正，防止延迟写入覆盖新值。

**阶段出口**：旧请求号移出窗口仍能找回，v1 更新到 v2 后使用新值，同账号的两个工单互不干扰，Redis 重启后状态可恢复。继承字段可以追溯到原始记录。

## 阶段 2 · 统一组装与预算控制

- [x] 接入生产图的统一上下文入口。路由、工具规划和答复节点共享本轮作用范围，各自读取必要字段。
- [x] 实现历史按需回查。处理「第一次失败」「刚才那个请求」等指代与字段冲突，带回少量授权原话及其消息 ID。
- [x] 实现按完整轮次裁剪。优先去掉重复检索片段和冗长旧工具输出，保留关键字段及原回执引用，维护工具调用与结果配对。当前问题、最新纠正、待查事项和必要引用优先保留。[DSH 上下文压缩](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/README.md)
- [x] 实现证据时效检查和重查。过期业务结果可用于定位查询对象；确认当前状态时重新查工具，失败时明确说明未核实。
- [x] 沿用现有预算进行第一轮对照，记录输入 token、首段延迟和裁剪后的关键字段保留情况。

**阶段出口**：超预算后可以继续原工单，关键例外和引用仍在，过期状态会触发查证。原有冻结 60 条回归继续通过，普通问答不会误继承旧工单。

## 阶段 3 · 按需摘要与长流程恢复

- [x] 验证无摘要版本。长工单追问只返回诊断结论，遗漏历史尝试、回退和待查事项。
- [x] 引入按工单范围的滚动进度摘录。持久化尝试、客户反馈和待查项对应的原始消息 ID，按需从同一会话提取有界的脱敏原话。沿用活动工单的排查锚点。
- [x] 验证摘要去重、当前范围限制和查询超时回退。摘要不会改变已核验实体和业务回执。
- [x] 对照相同真实入口的有无摘要版本。关键信息覆盖从 0/5 到 5/5；没有增加摘要模型调用。用量和首段耗时已记录。阶段 4 再验证真实模型上重复排障和延迟的变化，默认保留显式启用开关。

**阶段出口**：有数据说明摘要改善了哪些场景及其成本。摘要不可用时，核心续办与业务核验仍然成立。

## 阶段 4 · 观测、发布与回滚

- [x] 按生成 ID 记录上下文来源、裁剪、回查、组装耗时以及范围差异。隔离 OTLP 接收器验证了字段，未收到实际实体值。
- [x] 做影子对照。旧逻辑正常回答，新逻辑旁路选择工单和实体，并记录当前业务事实的重查意图。核对了跨窗口请求号的选择差异。
- [x] 用隔离 Docker 的候选镜像走正式 HTTP/WebSocket 验收 Redis 掉线、API 重启、用户纠正、跨工单和跨账号隔离。相关测试验证迟到的旧轮次无法覆盖新纠正。
- [x] 用真实模型复测两组长会话及原有冻结 60 条。跨窗口续办、纠正、隔离和五项进度恢复均通过。冻结题保留原答复，修正通用引用解析后按同一严格门槛复算。
- [x] 演练暂停放量和配置回滚。模拟确认串用后，放量门禁返回阻断。切回旧策略后，原始记录仍能通过正式历史接口回查；恢复新策略后可继续原请求。

**阶段出口**：交付候选镜像、长会话对照报告、观测字段与回滚记录。值守可以按生成 ID 区分保存、选取、裁剪和证据使用故障。

## 统一验收与交付顺序

同一账号在同一会话中走真实入口，把关键原话推到超过 **20 条消息和 12,000 字符**之后再追问。每类用例按预期应继承和预期应隔离成对设计，例如继续同一请求与明确切换请求、沿用版本与纠正版本、引用历史结论与重查当前状态。保留逐轮读取、工具调用、最终答复及来源的验证记录；涉及数据隔离时同时覆盖同账号不同工单和不同账号。

阶段 0–2 是第一版模块主干，阶段 4 是上线条件。阶段 3 的摘要依据前两阶段的实测缺口决定是否启用。先交付数据契约和真实入口基线，再围绕整套模块推进实施。
