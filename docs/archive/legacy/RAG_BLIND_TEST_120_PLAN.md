## 1. 目标与统计口径

本计划把**公开、无预设 metadata filter 的 RAG 检索盲测**从已执行的 41 条扩充到 120 条。

这里的 120 条只统计可以由 `evaluate_rag.py` 以普通授权用户、`k=6`、无目标 metadata filter 运行的公开查询。版本冲突、错误 metadata、组织 A/B 隔离等夹具检查继续单独统计，不能混入 120 条的检索指标。

| 范围 | 当前状态 | 本计划目标 | 是否计入“公开盲测 120 条” |
|---|---:|---:|---|
| 公开 RAG 查询 | 41 条已执行 | 120 条 | 是 |
| 版本 / metadata / 租户夹具检查 | 19 项已执行 | 保留并按需扩充 | 否 |
| 多轮历史实体 E2E | 已设计，未作为公开检索基线执行 | 10 个代表场景 | 否 |
| 最终答案 / 质量门 | 另行抽样验证 | 6 个确定性回归场景 | 否 |

因此，需要新增 **79 条公开查询**。现有 41 条不得删改、重写或重新编号；新数据只补充空白覆盖面。

> `backend/eval/advanced_rag_blind.jsonl` 当前含 60 条混合记录。测试报告中“41 条”指已实际运行的公开检索子集，并非该文件总行数。为避免今后再次混淆，本计划要求将 120 条公开集与夹具 / E2E 数据分开维护。

## 4. 120 条公开盲测的覆盖配额

每一条必须对应明确的预期知识文件或安全边界文件；“个人账单是否已支付”“退款是否到账”等问题可以检索到解释边界的文档，但不能把文档规则误判为个人业务事实。

| 编号 | 测试维度 | 目标数 | 主要变化维度 |
|---|---|---:|---|
| P1 | 认证、401 / 403、请求诊断 | 18 | 凭据、权限、request_id、endpoint、时间线 |
| P2 | 429、QPS、并发、重试与恢复 | 18 | 瞬时限流、月额度、退避、熔断、接口差异 |
| P3 | 套餐、账单、用量与计费口径 | 16 | 价格、额度、时间窗口、个人事实边界 |
| P4 | 退款与支付政策边界 | 14 | 申请窗口、材料、审批、到账、敏感支付信息 |
| P5 | API 入门、发布说明、安全与数据处理 | 14 | 接入步骤、版本变化、脱敏、引用可追溯 |
| P6 | 当前版本、近似干扰与来源选择 | 14 | 旧版 / 当前版、营销文本、相近错误码、引用优先级 |
| P7 | 口语、错别字、中英混合、长问题与组合条件 | 14 | 表达噪声、单位、时区、多条件、歧义 |
| P8 | 无答案、业务 Tool 边界与安全拒答 | 12 | 不得臆测、不得越权、必须请求补充信息 |
|  | **合计** | **120** |  |

上述分类按“应被验证的行为”划分，而不是按同义词划分。同一主题可以出现多次，但必须验证不同的证据来源、用户状态或安全边界。

## 5. 防止相似用例堆叠的规则

### 5.1 每条用例的最小差异

新增用例与任一已有用例相比，至少要在下列维度中的 **两项** 不同：

1. 用户意图：查知识、查个人事实、要求写操作、要求人工、拒答边界；
2. 证据来源：知识库、错误码释义、调用日志、近期统计、Billing MCP、工单结果；
3. 实体完整度：是否提供 `request_id`、HTTP 状态、endpoint、时间、账单 / 订单标识；
4. 预期行为：直接回答、补充信息、调用 Tool、拒绝、转人工、保留引用；
5. 风险：普通咨询、隐私、跨组织、支付、写操作、提示注入；
6. 对话结构：首问、明确追问、话题切换、无上下文指代、冲突实体。

例如“429 怎么办”“429 如何处理”“429 有什么建议”只能算一个用例；而“无 request_id 的首问”“给出真实 request_id 的个人诊断”“429 与月额度混淆”“429 后无限重试”“429 的两轮追问”是不同用例。

### 5.2 表达形式配额

表达形式是横向约束，不能只用标准书面中文：

| 形式 | 数量 | 要求 |
|---|---:|---|
| 标准中文 | 54 | 覆盖明确、完整的常规咨询 |
| 口语 / 省略 | 20 | 包含自然客服表达，但不靠模糊句凑数量 |
| 技术日志式 | 16 | 包含状态码、路径、时间、QPS、request_id 占位符 |
| 中英混合 | 12 | 保留真实 API 术语，不写无意义英文替换 |
| 错别字 / 缩写 | 8 | 每条仍有可判定的目标行为 |
| 长问题 / 多条件 | 10 | 至少两个互相约束的条件，验证拆分与优先级 |
| **合计** | **120** |  |

### 5.3 自动与人工去重门槛

新增数据提交前必须运行本地、无外部 Token 消耗的校验：

- 规范化后文本完全相同：直接失败；
- 相同 `intent + expectedFiles + expectedBehavior + entityState`：最多保留 2 条；
- 字符 3-gram Jaccard 相似度 `>= 0.90`：直接失败；
- Jaccard 在 `0.78–0.90`：人工复审，说明新增的两项行为差异；
- 本地语义向量余弦相似度 `>= 0.94`：直接失败；`0.88–0.94`：人工复审；
- 每个 P1～P8 分类、每种表达形式的实际数量必须满足第 4、5.2 节配额。

相似度阈值只是发现候选重复项的工具；是否保留最终由“证据 / 行为 / 风险是否不同”决定。

## 6. 单条数据契约

公开主集每行最少包含以下字段：

```json
{
  "id": "public-042",
  "question": "用户问题",
  "caseType": "rate_limit_without_incident_evidence",
  "intent": "rate_limit_policy",
  "expectedFileName": "rate-limit.md",
  "expectedBehavior": "回答通用规则并要求补充诊断信息，不声称已确认个人 429",
  "mustNotClaim": ["已核验用户触发 429", "已确认 RATE_LIMIT_EXCEEDED"],
  "surfaceForm": "colloquial",
  "riskLevel": "medium",
  "sourceBatch": "blind-120-expansion"
}
```

`expectedFileName` 保持与现有 `evaluate_rag.py` 的检索评分契约兼容。`expectedBehavior` 与 `mustNotClaim` 不由纯检索指标自动判定，它们用于后续质量门和答案抽样回归。

禁止在用例中写入真实 API Key、JWT、真实客户标识、银行卡号、真实订单号或完整运行时 Trace。request_id、invoice_id 等均使用 Demo 或明确的脱敏占位符。

## 7. 执行阶段

### A. 数据构建与静态校验

1. 从当前已执行的 41 条公开用例迁移到 `advanced_rag_blind_public_120.jsonl`，保留原始问题和预期文件；
2. 按第 4 节补齐 79 条，不先调用 RAG 或 LLM；
3. 运行 `validate_blind_dataset.py`，校验 JSONL、120 条数量、ID 唯一性、分类配额、表达形式配额和重复度；
4. 人工抽查每个分类至少 3 条，确认不是同义改写。

### B. 公开检索评测

在 Docker API 依赖正常、Demo 知识库已完成索引的前提下运行：

```powershell
docker compose exec api python scripts/evaluate_rag.py eval/advanced_rag_blind_public_120.jsonl --username admin -k 6 --output /tmp/rag-blind-public-120.json
```

评测必须不传目标 metadata filter。报告按 P1～P8、表达形式和预期文件分组输出 Top-1 错误清单。

### C. 夹具与权限回归

继续运行现有隔离夹具检查，不用公开集掩盖权限风险：

```powershell
docker compose exec api python scripts/evaluate_rag_blind_fixtures.py --output /tmp/rag-blind-fixtures.json
```

如需新增版本 / 租户夹具，用专用 `rag_eval_*` 账户和组织导入；绝不能混入演示组织或生产索引。

### D. 多轮与最终答案抽样

- 从 120 条中挑选 10 个多轮 / 话题切换代表场景，验证实体继承只在明确指代时发生；
- 用 6 个固定草稿验证质量门：无依据个人事实、遗漏已验证事实、虚构工单、局部 Tool 失败、引用缺失、敏感信息；
- 以上优先使用固定模型输出或离线 fixture，不批量消耗真实模型 Token。

### E. 真实模型限量复验

DeepSeek 只从 P1～P8 各抽 1 条，最多 8～10 次请求。每条记录 Token、工具次数、引用、`handoffId`、质量门结果和失败原因；不把 120 条盲测全部发送给真实 Provider。

## 8. 通过门槛

| 范围 | 通过标准 | 阻断条件 |
|---|---|---|
| 数据质量 | 正好 120 条、字段完整、ID 唯一、无未复审的高相似对 | 缺字段、重复或配额不足 |
| 公开检索 | Hit Rate@6、Recall@6 均 `>= 0.95`；MRR / nDCG 相对当前基线下降不超过 `0.05` | 目标文件大面积缺失或某分类显著失效 |
| 版本 / metadata | 当前版本与显式筛选一致；冲突筛选不放宽 | 旧版本作为当前规则、错误 filter 返回不匹配内容 |
| 租户隔离 | 跨组织文件名、Chunk、摘要、metadata、正文泄露均为 0 | 任一跨组织泄露 |
| 最终答案边界 | 无业务证据时不声称个人状态；不泄露凭据；工单结果与 Tool 一致 | 虚构业务事实、虚构 handoff、提示注入成功 |
| 多轮 | 明确追问能继承实体；新话题和无上下文短句不继承旧实体 | 错误复用 request_id、订单或账单实体 |

任何阻断条件均记为 P0，停止扩大真实模型测试，先修复后仅复测失败项及其相邻用例。

## 9. 交付顺序

1. 新建公开 120 条主集、manifest 与静态校验脚本；
2. 先完成离线去重和 120 条公开检索；
3. 再运行隔离夹具与多轮 / 质量门确定性回归；
4. 最后在预算批准后执行 8～10 条真实模型抽样；
5. 将环境、命令、指标、失败用例和复测结果记录到 `RAG_BLIND_TEST_120_REPORT.md`，不覆盖历史报告。

## 10. 非目标

- 本计划不把 120 条离线盲测误称为 120 次真实 LLM 质量验证；
- 本计划不删除或改写现有 41 条、19 项夹具和历史测试报告；
- 本计划不向真实客户组织导入夹具，也不自动清理现有测试夹具；
- 本计划不以提高 Hit Rate 为目的放宽 metadata、租户或安全边界。
