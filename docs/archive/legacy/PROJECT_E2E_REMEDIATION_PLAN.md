# PaiSmart E2E 问题修复计划

> 历史记录：本文保留当时的语料、实现和执行结果，不代表当前系统状态。当前结论见 [第一阶段验收](../reports/RAG_PHASE_ONE_ACCEPTANCE.md)，历史导航见 [历史索引](../README.md#legacy)。


状态：第一轮实现完成；受控复验已执行，Live 成本与部分质量门仍待优化\
依据：[完整 E2E 执行报告](PROJECT_E2E_TEST_REPORT.md)（2026-09-09）\
边界：本文件记录修复与受控验收；不运行批量真实评测，不自动扩大模型调用范围。

## 1. 修复目标

把已经跑通但尚不稳定的 Demo 主链路收敛到可演示、可回归、成本受控的状态：

1. Demo 用户检索不到 RAG 评测夹具；
2. 已有有效证据的政策、故障和账单解释不再被安全门误降级；
3. 同一次请求不重复执行语义相同的 Tool，LLM 调用有明确上限；
4. API 容器重建后，前端无需重启也不会因旧 IP 返回 502；
5. 离线测试全绿，普通用户有清晰的聊天历史入口。

这不是降低安全标准：涉及个人退款状态、账单、权限与工单的回答仍必须经过身份、工具结果和权限校验；证据缺失、冲突或越权时仍应安全兜底或转人工。

## 3. 实施顺序

先解决数据隔离和离线可复现性，再调整回答与调用控制，最后修复部署与界面入口。这样能避免测试夹具继续影响答案，也不会在未控成本前重复执行 Live 测试。

```text
R1 评测夹具隔离 ─┐
R5 离线契约修正 ─┼─> 离线回归全绿 ─> R2 回答质量 ─> R3 成本控制 ─> 小样本 Live 复验
R4 Nginx 动态解析 ┤
R6 普通用户历史入口┘
```

## 4. 分项修复设计

### R1：RAG 评测夹具隔离与安全清理

修改范围：`backend/scripts/seed_advanced_rag_fixtures.py`、检索层、Compose 测试 Profile、RAG 相关测试和运维文档。

1. 为盲测夹具提供只清理自身数据的 `--cleanup` 动作；只允许按固定 owner `rag_eval_fixture_owner` 和受控 `fixture-` 标识删除，先输出待删除数量再执行。
2. 后续将盲测夹具迁移到独立的评测索引（或独立的测试 Compose Profile）；正常 Demo 检索只读 Demo 索引。评测索引名必须带环境/运行标识，不能与生产或 Demo 默认别名相同。
3. 在迁移完成前，给检索层增加明确的评测夹具排除条件，防止 `fixture-*` 作为公开文档进入普通用户检索结果。
4. 实施前先统计当前共享索引中的 fixture 文档、备份其元数据和数量。对现存夹具的实际删除属于可恢复性较低的数据操作，实施时单独征得确认。

验收：普通用户查询“退款政策是什么”不含 `fixture-*`；盲测仍能在专用索引中运行；权限隔离测试不回归。

### R2：安全门从“格式拦截”改为“证据与权限校验”

修改范围：`backend/app/agent/graph/workflow.py`、`backend/skills/*/scripts/audit_*_answer.py`、最终回答提示词、对应单元和集成测试。

1. 将最终回答的引用规范统一为可机器校验的“来源 #n”格式，并由 Evidence Summary 提供允许引用的文档集合。
2. Quality Gate 同时判断结构化证据、引用编号、问题与证据主题一致性、业务权限四项；不能只因 LLM 未输出某个字面格式就判为“证据不足”。
3. 把“通用政策说明”和“个人业务事实”拆开校验：前者有可信知识证据即可回答；后者必须有当前用户身份和对应 Tool 结果，缺一不可。
4. 保持 Fail-Closed 边界：引用不存在、引用与结论冲突、个人退款/账单未核验、越权访问时，返回安全说明或转人工，不生成猜测性结论。
5. 增加固定答案回归：政策问答、429 诊断、已核验账单解释、未核验退款、伪造引用、冲突证据各一条。

验收：有有效证据的政策类问题得到事实回答和可点击/可追溯引用；未核验个人信息仍不能被回答；上述六类离线回归全部通过。

### R3：Tool 去重、回合限制与 Token 预算

修改范围：Target Agent 规划器、Workflow 调度状态、Tool Runtime / Trace、用量账本和测试。

1. 在一次 generation 级别维护调用指纹：`tool_name + 规范化安全参数 + 业务上下文标识`。相同指纹只允许执行一次；不同参数的合法查询仍可执行。
2. 统一由 Workflow 管理已执行调用，不让各专业 Agent 各自维护孤立的 `attempted_tools`；在 Trace 中记录“去重跳过”“达到预算”“正常执行”的原因。
3. 设置明确上限并配置化：每次 generation 的规划轮数、Tool 调用数、LLM 轮数和输出 Token 上限。超过上限时停止重规划，并以已有证据回答或安全转人工，绝不自动无限循环。
4. 将用量记录与 Trace 的每次真实模型调用关联，区分 LLM、Embedding、Tool；增加单请求 Token 汇总字段，便于后台监控异常成本。
5. 先用 mock / 离线 Trace 回归验证，不因调试而调用真实 DeepSeek。

建议初始门槛：常规政策问题不超过 4,000 LLM Tokens，故障诊断或明确人工转接不超过 6,000；超限即记录原因并停止。门槛在首次复验后可基于真实 Trace 调整，但不得放宽为无上限。

验收：相同 Tool 指纹每 generation 至多一次；重复调用场景有可读 Trace；预算触发不会重试；7 条历史 E2E 的离线重放不再出现无意义重复。

### R4：Nginx 对 Docker API 服务动态解析

修改范围：`frontend/nginx.conf`、Compose / 前端容器回归检查、Docker 运维文档。

1. 使用 Docker 内置 DNS `127.0.0.11` 配置 Nginx 定期解析 `api` 服务名，并让 `proxy_pass` 使用运行时变量，避免仅在 Nginx 启动时缓存容器 IP。
2. 分别保留 `/api/` 与 `/proxy-ws/` 的 URI 语义、升级头和超时设置；不能因修复 HTTP 登录而破坏 WebSocket。
3. 添加可重复的容器重建验收：前端持续运行时重建 API，随后验证健康检查、密码登录和 WebSocket 连接。
4. 在运维文档注明旧版本的临时恢复方式（重启 frontend），并在修复后标记为仅应急手段。

验收：API 容器 IP 变化后，前端登录和 WebSocket 均不出现 502；不依赖人工重启 frontend。

### R5：WebSocket 多轮 Tool E2E 契约

修改范围：`backend/tests/e2e/test_websocket_architecture.py` 及关联 mock。

1. 明确该测试验证的是“搜索子块后按需要读取父文档”的两轮契约，还是“模型可选择只搜索一次”的最小契约；不要把未模拟的第二轮行为写成必然断言。
2. 若验证两轮链路，mock 必须按实际 state / replan 条件产出第二轮 `get_document`；若验证最小链路，删除不成立的 `get_document` 断言，并另建一条父文档读取专项测试。
3. 保留现有 WebSocket 鉴权、事件顺序、最终 completion、handoff 与 Safety 节点断言。

验收：`docker compose --profile test run --build --rm test pytest -q tests` 全绿；测试能说明失败时是 Workflow 回归还是夹具失真。

### R6：普通用户聊天历史入口

修改范围：前端路由、侧边栏、用户会话 API 的权限测试、E2E 方案。

1. 增加普通用户可见的“聊天记录”入口，指向仅展示本人会话/消息的页面或现有对话列表增强页；不复用管理员的全局筛选页。
2. 页面只请求当前用户范围的会话数据，支持进入单个会话；管理员菜单与普通用户菜单继续严格隔离。
3. 将 E2E 方案的“普通用户打开聊天记录”改为与最终 UI 路由一致的可操作步骤。

验收：普通用户登录后可从显式菜单进入历史记录；只能看到自己数据；管理员仍可使用全量 `/chat-history`。

## 5. 回归与 Live 复验矩阵

| 阶段 | 运行内容 | 外部模型调用 | 通过标准 |
|---|---|---:|---|
| A. 代码级 | 单元测试、Safety Gate 固定样例、Tool 指纹/预算、fixture 可见性 | 0 | 所有新增测试通过 |
| B. Docker 集成 | 全量 `pytest`、API 重建后的登录/WebSocket、普通用户历史页面 | 0 | 全量测试全绿；无 502；权限无回归 |
| C. RAG 专项 | 隔离索引上的盲测子集与 Demo 索引污染检查 | 0 | Demo 检索零 fixture；评测索引结果可复现 |
| D. 受控 Live | 最多 4 次 DeepSeek 请求：退款政策、401+追问、明确人工转接 | 最多 4 次 | 每次有 completion、Trace、账本记录；回答/引用/去重/预算均满足目标 |

Live 阶段必须在 A、B、C 均通过后才开始。禁止自动重试、循环提问或批量模拟 60 条问题；若任一次达到预算或质量门失败，停止 Live 并回到离线修复。
