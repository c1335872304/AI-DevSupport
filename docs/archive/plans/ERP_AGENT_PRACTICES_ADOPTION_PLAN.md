## 阶段 1 · 统一写入授权、幂等与回执

借鉴 ERP 在审批恢复和实际写入两处校验的做法。先把工单创建接到同一写入契约，普通工单按现有业务授权处理。将来实际接入退款、改套餐等高风险动作时，再依据业务政策启用人工审批。 [ERP 写操作闭环](https://github.com/wodrake/ERP-AGENT-open-source#2026-11-18-更新写操作安全闭环与工程化基线)

- [x] **1.1 定义动作注册。** 建立一个写动作清单，逐项声明授权方式、允许字段、幂等范围和成功回执校验。盘点所有能调用工单创建的路径，保证它们在实际写入前汇合到同一个业务边界。
- [x] **1.2 定义授权凭据。** 由服务端绑定用户或租户、动作、目标、规范化参数和有效期。将来接入人工审批时，批准与该次执行绑定。更换动作或关键参数时重新取得授权，旧批准无法恢复新的执行。
- [x] **1.3 定义幂等与并发规则。** 同一个逻辑动作重试复用原键。相同键和相同载荷返回已确认结果，相同键但载荷不同返回冲突。优先复用现有唯一约束与业务事务，验证并发请求只产生一次业务写入。
- [x] **1.4 核对提交后的不确定状态。** 当前本地建单路径已验证提交前受控重试、提交后按原键恢复以及用已落库对象确认成功。将来接入外部写入系统时，再验收其未知状态与回执核对。
- [x] **1.5 补齐审计和发布兼容。** 记录授权、执行、拒绝、重放和结果的关联标识。保留旧工单查询和续办能力。涉及新增字段或约束时，用已有工单验证迁移和回滚。
- [x] **1.6 做业务故障验收。** 以正式入口验证正常成功、未登录拒绝、进程重启、并发重试、提交前失败、提交后丢回执与跨账号访问。服务端写入边界另外验证缺失或过期授权、载荷冲突与取消并发。人工审批启用的动作另测拒绝、过期和重放。逐项对照动作记录、工单表与用户收到的回执。

**阶段门槛**：无授权写入为 0，同一逻辑动作重复落库为 0，虚报成功为 0。重试能恢复原回执，既有工单链路复测通过。业务表和动作回执均留证。

本轮本地验证。全量回归 389 通过、2 跳过。随后加入普通工单提交回执丢失的回归，工单与诊断定向测试 41 通过。隔离 SQLite 测试核对了三种未授权输入零落库、同载荷并发只落一张、不同载荷报冲突、回执丢失恢复同一张。冻结离线回归 60/60、30/30 对、38/38 项指定引用通过，供应商调用为零。本轮证据覆盖服务边界和本地回归，正式入口故障矩阵仍按 1.6 验收。[定向回归](../../../backend/tests/agent/test_handoff_write_boundary.py)

第二轮实现与验收。

- 诊断新建工单要求属主匹配、服务端租约对应当前生成及 epoch、租约在有效期内、持久化状态为 `HANDOFF_PENDING`。实时工具与后台恢复都在持有诊断锁的写入事务中验证这些条件。工单载荷统一从已持久化的诊断决定生成。已落库工单可按原诊断 ID 恢复。
- 普通工单首次写入要求属主一致且生成处于 `STREAMING`。生成进入终态后仍可按原载荷取回已存在的回执。共享服务日志记录授权、拒绝、重放、核对和成功确认，关联生成 ID、诊断 ID 或工单 ID。计划仍需验收普通工单授权与载荷的显式绑定及审计留存。
- 使用本机镜像 `paismart-backend:context-no-request-final-20261118` 的依赖、当前源码只读挂载、隔离 SQLite、容器内模型替身和无外部网络的临时容器。既有演练脚本通过正式 HTTP/WebSocket 跑 `handoff-before` 和 `handoff`，各三轮均通过。前者确认提交被拒绝后零落库且恢复后只建一单，后者确认回执丢失后三路并发恢复取得同一工单。容器和临时数据已清理，本段保留验收摘要。完整矩阵仍需在同一发布候选上验收。[故障演练脚本](../../../backend/scripts/run_phase_b_docker.py)
- 后端全量回归 390 通过、2 跳过。补齐普通工单终态授权用例后，工单与诊断定向最终回归 43 通过，覆盖缺租约、过期租约、终态阻止首次写入与已有回执重放。
