日期：2026-10-20。P4-01～P4-08 已实现和验收；可选 P4-09 截图输入未实施。范围见[四阶段计划](../FOUR_PHASE_ITERATION_PLAN.md)，过程见[第四阶段检查点](PHASE_FOUR_PROGRESS.md)，操作见[三条演示](../03-operations/PROJECT_DEMOS.md)和[质量门禁](../03-operations/CI_PLAN.md)。

本轮没有更新或重新编码当前知识库，没有修改实际 `.env`，没有重建原 Docker Demo。实际改动是冻结评测、轨迹评分、三组对照、停止冗余 API 规划、反馈连续性修复、CI 和交付材料。

## 冻结输入与评分

`backend/eval/phase4/manifest.json` 保存输入 SHA、起点源码/查询向量摘要、门禁和机制分层。诊断24个任务：8开发、16保留，覆盖八种原因、缺观测、未知版本/字段、冲突、跨用户、超时、修正后成功/仍失败/关联拒绝、用户反馈、无进展和交接。

保留子集由本地编写，不是第三方独立盲测；120条检索题是既有官方语料回归集，不是新保留集。索引并发、版本清理、修订/删除、费用防重、ACL撤权和执行恢复通过冻结的机制测试分组另外验收，不能用改写问法增加覆盖声称。

评分读取实际 AgentRuntime 产生的工具参数、业务证据、候选、复查、状态及真实测试工单；标注不进入运行时。评分器的反例测试覆盖无权/未验证证据、文档冒充业务、无来源参数、伪造解决和重复工单。零分母返回不可用。自然语言答复仍经过现有质量门；“无依据候选比例”不等于所有自然语言事实的普遍错误率。

## 索引可靠性对照

运行冻结旧 `indexer.process_file`，使用两个真实 SQLite 连接，使A发布后暂缓清理，B完整发布后再继续A清理。最终指针指向B，但B活动向量数为0，复现宽泛删除其他版本的问题。编码、对象存储和ES明确使用测试替身；没有调用旧代码处理当前知识。

最终实现的 `test_gc_interleaved_with_new_publication_keeps_new_version` 在真实 MySQL/ES 中通过，活动向量仍可读。该对照证明这个交错场景得到修复；不外推成任意并发条件下的失败率。报告：`phase4/index-cleanup-comparison.json` 与 `phase4-integration.xml`。

## 修复记录与限制

- 完整聊天中的“已恢复”此前会丢失故障连续性，现保留为原诊断的未核验用户反馈；不会自动标解决。
- 首轮状态标注把用户反馈写成待用户动作，实际契约应等待复查；评分也曾错误使用拒绝复查后保留的历史候选。修正标注和评分对象后重新冻结，原失败轨迹保留。
- 真实验收曾把合法的零模型调用当成用量缺失，修正为只有实际调用却缺用量才失败；第二轮通过，两轮用量都计费记录。另修复Windows默认GBK读取UTF-8报告；该次启动失败未发请求。
- 将第三阶段截图复制到可交付文档资源目录，避免CI引用被忽略的本地data文件。
- 6个检索失败仍在；不引入缺乏测量依据的重排器或全库重编。真实模型样本很小，没有普遍准确率、成本优化率或生产性能结论。
- 截图输入、扫描OCR、大集群调度、生产滚动发布、高可用与容器全量重建未纳入。当前配置保留，部署前须独立确认目标Provider模型；原Docker运行状态不能由本轮源码测试证明。
