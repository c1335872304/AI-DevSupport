# 稳定证据前缀：Docker实现与缓存验收

2026-10-20；长任务完成实现、回归、部署和实测。固定提示词仍在最前，简单文档题现在按“最终证据稳定排列 → 当前问题”发送。收益集中在同一证据被不同问法复用时；首次新格式调用仍会承担冷启动成本。

## 最终实现

修改 `backend/app/agent/document_context.py` 和 `backend/app/agent/graph/workflow.py`，仅影响已通过保守分流的独立单厂商文档题。比较、历史会话、账户/账单操作和401/429诊断继续原有流程。

1. 先按原有相关性、主要片段和限制条件选择证据，保留相邻解释；排序不提前到选材之前，检索top_k、权限、版本过滤和预算不变。
2. 对已选块按文件名、文件身份、索引版本、分块位置、页码和块内位置形成稳定顺序。同文档同版本的去重与重叠合并也按确定顺序执行，保留否定和范围保护。
3. 对最终来源集合按稳定身份重新编号为1～N，同步重标块的refs、完整签名引用映射和最终evidence_summary。原始读取轨迹保留，并记录旧编号到新编号的映射事件。
4. 模型侧JSON字段顺序固定为 `sources → excerpts → question`，固定系统提示词在前；签名、时间和内部定位信息不进入模型侧前缀。
5. 记录文档前缀SHA256和长度用于审计；身份冲突或必要内容超预算时继续按原有证据契约回退，不为缓存删除关键事实。

“固定编号”指同一最终来源集合不受检索名次、旧编号及签名字段变化影响，不是给每份文档注册跨所有回答永久不变的数字。来源集合变化允许重新编号。版本参与身份与排序、签名继续绑定具体版本；若正文与模型侧内容完全相同，版本更新仍可复用模型计算，实际引用按本次版本校验，不复用旧答案。

## 缓存实验结果

这里的命中率统一为 **缓存命中输入Token ÷ 总输入Token**，不是“某次请求是否命中过任何一个Token”。

实验从三家官方资料的已授权真实检索结果冻结选材后的证据。每组依次执行首次问题、换问法并反转来源顺序、再换问法并旋转来源顺序、完全重复首次问题。两版各3组×4次，均实际调用原配置模型生成，没有复用答案。不同组交错执行，为落盘留出间隔。

| 固定证据实验 | 旧格式 | 新格式 |
| --- | ---: | ---: |
| 首轮构建，3次输入Token命中率 | 3.52% | 3.52% |
| 换问法/改来源顺序，6次命中率 | 3.52% | 95.13% |
| 上述6次估算费用 | ¥0.026410 | ¥0.006216 |
| 上述6次平均耗时 | 1.456秒 | 1.437秒 |
| 完全重复首次问题，3次命中率 | 95.07% | 95.13% |
| 包含首次构建的全部12次命中率 | 26.41% | 72.23% |
| 全部12次估算费用 | ¥0.043573 | ¥0.022997 |
| 全部12次平均耗时 | 1.464秒 | 1.432秒 |

换问法场景的费用下降76.5%，输入费用本身约下降93%；平均耗时仅改善约1.3%，视为基本持平。包含首轮构建的12次总费用下降47.2%。输出Token也有波动，不能将所有费用差异都视为输入缓存收益。

新格式每组四次的文档前缀哈希完全一致，第1/4次完整消息哈希也相同。完全重复同题的旧格式同样可以高命中，因此改动的价值是保持证据前缀，而非让原本不能缓存的接口突然具备缓存能力。

两版、各组使用独立固定实验标记，减少历史热文档前缀影响；生产提示词和配置没有加入该标记。该实验固定选材、直接走原LLM生成接口及相同答复过滤，不重新检索，也不经过聊天计费预扣流程；费用仍按真实Provider usage统计。它验证排列与前缀机制，不能代替真实检索或代表所有生产问法。

## 真实检索首轮：冷启动没有被算成节省

两版分别用同一14题，通过真实HTTP/WebSocket完成检索、工具、答复及引用检查。六道文档题仍各一次模型生成和一次查询编码，没有额外暖缓存请求。

| 首轮6道简单文档题 | 旧版本 | 新版本 |
| --- | ---: | ---: |
| 输入Token合计 | 23569 | 23566 |
| 缓存Token命中率 | 53.76% | 3.26% |
| 平均端到端耗时 | 2.435秒 | 2.582秒 |
| 合计估算费用，含查询编码 | ¥0.016361 | ¥0.028602 |

新格式首轮的费用增加74.8%，耗时增加6.0%，主要受旧格式已有缓存、新格式文档前缀冷启动及输出长度波动影响。本次优化没有减少输入内容，也不能宣称第一次请求就更便宜。

14题整体估算费用为¥0.082474→¥0.091867，平均耗时4.264→4.789秒。未改动的诊断路径也存在规划轮数波动（LLM 27→30次），因此不能把整体耗时或调用量变化全部归因于文档排序。

## 回答质量与引用

自然端到端两版均 **14/14通过**：三家配置、跨厂商Schema比较、厂商不明追问，以及6个Demo诊断/复查/转人工场景。24次独立缓存实验答复也按冻结要求逐题核对通过。

- 文档题保留JSON参数及提示词前提、Qwen同地域/同计费方案与套餐专属地址例外、后台轮询状态、流式usage和非流式例外。
- 重编号后JSON文档、Qwen Base URL和后台模式的引用仍映射到正确原文；自然题引用接口分别92/92、99/99成功，没有未映射编号、越界厂商或文件名错配。
- 401按调用时过期Key证据处理；新请求200后同一诊断才进入RESOLVED，范围限该应用/接口。
- 429从RATE_LIMIT变为QUOTA_LIMIT后仍未解决；未知请求不编造原因；转人工有真实成功记录及工单号。

诊断记录属于本项目Demo服务，不代表查询三家厂商的个人账户。通过仅针对冻结要求，不等于完整代码示例可直接运行或所有问法无误；引用页脚仍可能列出未在正文使用的资料，既有地域计费表达问题未因此全部解决。

逐题证据：[旧版自然问答](STABLE_PREFIX_BASELINE_CASES_2026-10-20.md)、[新版自然问答](STABLE_PREFIX_FINAL_CASES_2026-10-20.md)、[独立缓存实验答复](STABLE_PREFIX_CACHE_PROBE_CASES_2026-10-20.md)。审阅由执行代理逐题核对，绑定原始产物SHA256，没有另花费用调用裁判模型，也不代表用户人工签字。

## 方法、费用和边界

自然题使用与部署API相同镜像和环境的独立18870端口，连接同一MySQL、ES、MinIO等服务；没有经过前端代理。每版前只重置冻结14题对应的应用路由缓存键，结束恢复原值及剩余TTL。无法清理或控制厂商KV缓存，因此两类实验单独报告，不把旧格式历史热缓存当成相同冷启动条件。

检索选材仍随问题变化。只有最终证据集合、片段和序列化前缀相同时，文档前置才有较大复用空间；稳定排序不会让不同证据自动相同。实验每种情况只有三家各一组，非随机交错两版，不作为长期平均延迟或成本承诺。首段时间在应用缓冲后记录，不等于模型侧原始首Token延迟。

根据[DeepSeek官方缓存说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)，命中取决于完整缓存前缀单元及落盘，系统尽力而为；本次第二次不同问题即出现高命中，不保证其他请求也如此。

合计28次自然问答、24次格式实验，共52次答复尝试；105次LLM请求与56次查询编码，共161次Provider请求，161次均捕获usage，全部估算费用 **¥0.240912**。诊断最终答复仍使用原有受约束渲染器，不把其标成新增的LLM回答调用。固定上限¥10及300次Provider请求，未触达。输入准备时曾误用筛选后的引用映射，已在首次付费格式实验前修正为完整候选映射，没有产生付费失败或重跑挑选。

本轮均为北京时间空闲时段。按已核验的[DeepSeek公开价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)（实际响应deepseek-flash，百万Token缓存输入¥0.02、未命中输入¥1、输出¥4）与[千问北京同步编码价格](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)（text-embedding-v4输入每百万Token¥0.5）估算，未扣赠送额度，未包含机器存储成本，未经厂商账单对账。配置模型名仍为deepseek-chat。
