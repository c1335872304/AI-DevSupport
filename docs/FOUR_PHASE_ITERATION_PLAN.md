## 目标与实施边界

围绕一个明确的 API 服务，将现有系统推进为可验证的 401/429 故障诊断助手：依据证据判断原因，跟踪处理过程，复查是否恢复，并在无法继续时完整交接人工。

沿用 FastAPI、LangGraph、三个专业 Agent、RAG、Tool Runtime 与 Billing MCP。API 诊断继续使用本地受控工具，Billing 继续通过只读 MCP 核查套餐、用量和账单。增加能力时优先扩展现有模块。

当前已具备请求日志、Key 状态、错误码与近期调用统计查询，实体记忆、证据汇总、质量门、检索 ACL、元数据过滤、版本化索引及分层评测。本计划基于代码和历史文档梳理；历史测试结果不能替代本轮验收。

业务状态允许由明确标注的模拟服务提供；模拟结果、确定性测试和真实模型效果分别报告。诊断与复查默认只读，用户执行修正后提供新请求号，系统不自动修改 Key、套餐或生产配置。

### 阶段目标

先保证知识链路正确：同一份文档被重复提交、多个 Worker 同时处理、旧任务晚完成或锁过期时，不能覆盖新结果或误删当前版本。随后完成适用版本、文档生命周期与权限变化验证。

### 任务安排

- [x] **P1-01 冻结基线与复现并发问题**：记录当前提交、配置、模型与工具版本、知识数据快照；保存检索与 401/429 典型案例的输出、轨迹、耗时及 Tokens。复现同 job 重复消费、不同 job 处理同文档、旧任务晚完成和清理交错场景，预留未参与调试的验收案例。
- [x] **P1-02 实现任务原子抢占**：在 `documents/jobs.py` 通过数据库条件更新或等效机制领取任务，校验受影响行数；保存执行者标识、尝试次数和租约信息，防止先读状态再写 `RUNNING` 导致重复领取。恢复任务只接管租约过期的执行，不能重置其他健康实例的任务。
- [x] **P1-03 实现文档级互斥与重复任务合并**：按 `file_id` 或稳定的用户/文档标识协调不同 job；明确占用时等待、合并或拒绝策略，不锁整个知识库。所有索引入口，包括 Worker、后台任务和脚本，都必须执行相同保护；多进程部署不能只使用 `asyncio.Lock`。
- [x] **P1-04 防止过期执行者发布**：使用可校验的构建代次/所有权标识；切换 `active_vector_version` 时，在数据库原子条件中验证任务仍持有有效发布权且输入修订未变化。若采用租约锁，明确续租、失锁处理和按所有者释放，锁过期后旧任务不得继续切换版本。
- [x] **P1-05 改造版本清理与失败回滚**：禁止并发执行者无条件删除“除自己版本外”的全部版本。记录构建、发布和失效状态，只清理已确认废弃且未被活动指针或在途构建使用的版本；清理与发布采用一致协调，处理 DB/ES 部分成功并支持重试。文档删除需阻止在途任务重新发布。
- [x] **P1-06 实现幂等写入与计费保护**：按文档、输入修订、Embedding/切分配置识别等价构建，重复提交复用已完成结果；同一构建内使用稳定 Chunk 标识和唯一约束。计费结算以明确的构建/尝试标识防重，区分重放同一结果与实际发生的新 Provider 调用；锁和幂等分别验收。
- [x] **P1-07 区分索引版本与知识适用版本**：补充产品、API 版本、有效起止时间和替代关系；检索按已知上下文过滤，缺少必要版本时返回待补信息。文档元数据或内容变化应形成可校验的输入修订。
- [x] **P1-08 处理冲突文档与证据不足**：在相同适用范围内检测矛盾材料，依据版本、时间和来源选择引用；无法裁决时保留冲突，不强行生成确定结论。当前检索任务不得靠预置正确过滤条件冒充自动识别成功。
- [x] **P1-09 验证知识生命周期**：覆盖新增、更新、删除、重建失败、发布和重试；过期/删除内容不进入后续答案，重建失败保留原有效索引。文档删除与任务取消、发布、清理保持一致。
- [x] **P1-10 验证 ACL 与缓存失效**：检索和正文读取均使用可信身份授权；权限撤回后不复用旧授权缓存，后续回答不能继续引用无权访问的内容。跨用户、跨组织分别设置案例。
- [x] **P1-11 完成 RAG 专项验收与说明**：通过可控执行顺序复现并验证上述竞争，不只测试单任务成功；记录原子抢占、发布条件、锁粒度、失锁、幂等和垃圾清理的职责，更新 RAG 架构与运维文档。
- [x] **P1-12 接入 Docling 解析**：在第一阶段批次 C 实施，完成写入与生命周期保护后支持文字型 PDF 和 DOCX；MD / HTML 沿用现有路径。固定解析器与模型版本，设置文件、页数、超时和资源边界；扫描件 OCR、旧 DOC 后续扩展。
- [x] **P1-13 保留解析结构与引用**：保存原文件、结构化 JSON 和 Markdown，统一标题、表格、代码及位置到内容块；PDF 保留页码与可用坐标，DOCX 按章节/块定位。配置纳入 Profile，仅对子块做千问编码，解析产物不重复入库编码。
- [x] **P1-14 验收多格式解析**：至少 8 份固定样本覆盖 PDF / DOCX、双栏、跨页表格、代码、扫描件和损坏文件；检查关键字段、表格对应、引用位置、失败保留旧索引，比较同内容跨格式检索并记录资源、耗时与 Tokens。详细依赖见 RAG 设计 C-06～C-08，完成后纳入 P1-11 总验收。

- 任务抢占、文档级协调、条件发布、幂等写入与安全清理实现。
- 知识适用版本、生命周期、冲突与授权变化规则及验收报告。
- Docling PDF / DOCX 适配器、解析产物与引用映射、固定样本、专项验收报告及模型缓存部署说明。

### 验收标准

- 同 job 重复消费仅一个执行者获得有效执行权；不同 job 处理同文档时符合既定等待/合并策略，不同文档仍能并行。
- 旧任务晚完成、锁过期或权限/输入修订变化后，失效执行者不能覆盖新版本。
- A/B 构建交错清理、发布中断与清理重试不会误删当前活动版本或其他合法在途版本；最终活动指针对应完整可检索内容。
- 等价重复提交不产生重复有效 Chunk 或重复结算；实际新增 Provider 消耗有独立记录。
- 文档重建失败不破坏原有效索引；删除不会被在途任务复活；权限撤回后新检索、正文读取和缓存均不泄露内容。
- 固定检索案例未发生未解释的回退，版本不明、文档冲突和证据不足均有可核查结果。
- PDF / DOCX 解析样本通过关键内容与来源定位检查；不支持或损坏文件不能以空内容发布成功，解析失败不影响当前有效索引。

## 第二阶段：诊断状态与证据标准化

### 阶段目标

在第一阶段可靠的知识与授权链路上，把一次诊断从聊天历史中独立出来，明确“查到了什么、哪些尚未确认、下一步做什么”。

### 任务安排

- [x] **P2-01 设计并持久化诊断对象**：新增 `DiagnosisSession`，关联用户、应用、聊天会话与多轮 generation；保存症状、实体、候选原因、证据引用、待补字段、下一步动作和结束原因，补齐数据库迁移。
- [x] **P2-02 实现状态转换**：支持收集信息、核查中、等待用户操作、等待复查、已解决、未解决结束、转人工；由程序验证转换条件，记录状态变更及触发依据。
- [x] **P2-03 统一证据结构**：标注来源类型、所属用户/应用、请求号、事件时间、查询时间、有效范围和支持的主张；区分用户描述、文档说明与业务查询事实。接入第一阶段的文档适用版本与来源，错误码定义不得直接支持个人故障结论。
- [x] **P2-04 修正调用统计窗口**：分别支持当前窗口和指定故障窗口；返回明确起止时间、统计范围与查询时间，避免以旧 429 锚点返回的历史统计被描述成当前状态。
- [x] **P2-05 收紧实体继承**：同一故障沿用已有实体；切换应用、请求或话题时重新判断归属。新增请求号不能被旧请求号覆盖，历史实体必须保留来源。
- [x] **P2-06 定义证据新鲜度**：按日志、Key 状态、配额、统计和文档规定复用条件，承接第一阶段的授权与索引失效机制；历史日志仍可解释历史事件，当前状态与恢复判断必须检查时效。
- [x] **P2-07 打通状态读取与前端展示**：提供当前用户的诊断详情读取接口；在对话中展示诊断状态、已确认事实、待补信息和下一步，证据列表只展示脱敏内容。
- [x] **P2-08 完成针对性回归**：覆盖多轮追问、换话题、未知请求号、证据来源混淆、历史统计、证据过期与跨用户读取；同步更新架构说明。

### 交付物

- 诊断数据结构、迁移、状态转换规则及读取接口。
- 统一证据契约、新鲜度规则与准确的统计时间语义。
- 多轮回归案例、诊断状态演示及阶段验收报告。

### 验收标准

- 同一故障不重复追问已有有效字段，新故障不误继承旧实体。
- 任何“已确认”个人事实都能追溯到相应用户、请求和时间范围的业务证据。
- 文档释义或用户口述不会被升级为工具已核验事实，过期结果不会被当成当前状态。
- 诊断详情严格按当前用户授权读取，关键状态转换有记录。

## 第三阶段：401/429 诊断闭环与执行恢复

### 阶段目标

在可靠知识和诊断状态基础上完成原因排查、处理建议与修正后复查，并保证工具超时、重复提交及服务重启时诊断状态一致。

### 任务安排

- [x] **P3-01 明确服务诊断规则与观测字段**：选择一个 API 服务形成原因矩阵；补齐认证缺失、格式错误、Key 失效/过期、应用不匹配，以及频率、并发、配额的必要脱敏证据。规则与第一阶段的适用版本保持一致，无法取得的字段明确标为不可判定。
- [x] **P3-02 实现候选原因管理**：每个原因记录待验证、已支持、已排除或无法判断，保存支持/反对证据和最后更新时间；禁止只凭 HTTP 状态码确认细分根因。
- [x] **P3-03 实现下一步选择**：根据证据缺口选择工具或追问；有依赖的查询分轮执行，独立只读查询并行，证据充分时停止重复调用。
- [x] **P3-04 处理诊断证据冲突**：用户描述与日志不一致时核对请求号、应用和时间；保留冲突及缺口，不能静默覆盖。日志只代表对应事件，不能外推为账户当前状态。
- [x] **P3-05 关联处理建议**：每条建议关联候选原因及依据，给出用户需要执行的最小动作和复查方式；禁止索取完整 Key、Token 或未脱敏认证头。
- [x] **P3-06 接入修正后复查**：接收新 request_id，核对用户、应用及故障关联，比较新旧状态；成功请求可支持对应范围内恢复结论，用户反馈恢复单独记录，不能冒充工具确认。
- [x] **P3-07 完成失败与交接路径**：复查失败继续排查；无进展、达到预算、需要人工权限或用户明确要求时交接，工单包含已查事实、尝试动作、未决原因和复查结果。
- [x] **P3-08 实现诊断步骤检查点**：保存已完成工具步骤、证据和待执行动作；重启后核对执行权与状态，恢复诊断并允许模型重新规划，重新核验过期证据。恢复范围限定为结构化状态，不承诺恢复模型内部推理。
- [x] **P3-09 完善失败分类与有限重试**：临时超时或服务故障按预算重试；参数错误、权限不足和不存在记录采用不同分支，记录尝试次数、最终状态及部分成功事实。
- [x] **P3-10 完善重复执行保护**：复用有效期内相同只读查询；验证工单幂等键与唯一约束；对执行结果不明的工单创建，先核实已有结果再重试。诊断恢复不得重复创建工单。
- [x] **P3-11 执行闭环回归与故障注入**：覆盖 401 各类原因、429 三类限制、无日志、冲突、用户反馈恢复、复查仍失败、工具超时、调用后持久化前中断、检查点后重启和重复提交；补充诊断过程中知识更新/撤权的跨阶段回归，更新运维说明。

### 交付物

- 服务原因矩阵、候选原因管理、下一步选择与修正后复查机制。
- 检查点恢复、失败分类、重复执行保护和人工交接实现。
- 401/429 成功闭环及未解决转人工演示、故障注入报告与恢复说明。

### 验收标准

- 401 能区分服务实际支持的认证失败原因，缺少证据时继续核查或说明无法确定。
- 429 频率、并发和配额问题分别有对应证据，仅凭 429 次数不能断言配额耗尽。
- “已解决”具有明确确认方式，区分业务复查与用户反馈，不错误关联其他用户、应用或不相关请求。
- 工具部分失败时保留成功事实，明确缺口并在预算内结束。
- 服务重启后能恢复诊断，恢复过程中重新核验过期证据。
- 重复请求及恢复重试不会生成重复有效工单，交接失败不得声称成功。

## 第四阶段：评测、成本优化与项目交付

### 阶段目标

以固定任务证明改进，在不降低诊断质量的前提下减少耗时和成本，形成可复现的项目成果。

### 任务安排

- [x] **P4-01 冻结分层评测集**：整合各阶段案例，按故障机制划分 RAG 并发写入、版本清理、知识生命周期、检索适用性、诊断、多轮复查、安全与恢复场景；区分开发集与保留验收集，避免只增加同义问法。
- [x] **P4-02 实现轨迹级评分**：检查工具选择、参数来源、原因判断、证据归属、复查行为、结束状态与工单结果；最终文字评分作为其中一层，不代替行为验收。
- [x] **P4-03 执行三组对照**：比较普通 RAG、第一阶段任何实现变更前冻结的系统基线和最终系统；统一任务、数据快照、模型配置和运行环境，报告可比较项及配置差异。检索与索引可靠性单独对照，普通 RAG 不支持诊断复查的指标明确标记为不适用。
- [x] **P4-04 输出核心指标**：统计 Hit Rate/Recall@K、MRR/nDCG、版本与授权适用性、并发构建一致性、重复写入/结算，以及原因判断正确率、无依据个人结论比例、工具/参数正确率、复查完成率、解决率、转人工准确性，以及 P50/P95、Tokens 和工具调用数；每项写明分母、样本数和失败案例。
- [x] **P4-05 根据轨迹优化开销**：减少不必要的 Agent 激活、重复检索、冗余上下文和无进展规划；复用有效证据，设置任务级工具与步数预算，每项调整后运行受影响回归。
- [x] **P4-06 执行受控真实模型验收**：先通过离线和模拟服务测试，再以明确的样本、调用上限、费用预算和停止条件进行真实模型测试。分别报告架构正确性、模拟闭环与真实模型效果。
- [x] **P4-07 接入质量门禁**：结合现有 CI 分层执行快速回归与集成测试；真实模型测试独立执行，不因外部 Provider 波动阻塞全部本地验证。修复影响本轮交付的构建和检查问题。
- [x] **P4-08 完成部署与演示材料**：整理启动步骤、模拟数据说明、三条完整演示、架构图、对照报告、成本记录、已知限制和排障说明；更新根 README 与文档导航。
- [ ] **P4-09 可选扩展：截图输入**：核心门禁通过后，才增加截图提取、字段确认和同一诊断流程接入；图片内容标为用户提供线索，不直接作为已核验业务事实。该项不阻塞核心四阶段交付。

### 指标口径

| 指标 | 统计口径 |
| --- | --- |
| 检索效果 | 在固定文档快照、K 值和标注下统计 Hit Rate/Recall@K、MRR/nDCG；自然查询与预置过滤的测试分别报告 |
| 版本与授权适用性 | 检查返回材料是否符合产品、API 版本、有效时间及当前身份授权，记录错版本、已删或无权内容的命中 |
| 索引并发一致性 | 对可重复的交错执行案例核对活动指针、DB/ES 有效 Chunk、合法在途版本及结算记录，逐项报告覆盖范围与失败次数 |
| 原因判断正确率 | 在预先标注为证据可判定的案例中，原因判断正确的比例；另报正确保留不确定性的比例 |
| 无依据个人结论比例 | 缺少适用业务证据的个人事实主张占所有个人事实主张的比例 |
| 复查完成率 | 应进入复查的案例中，实际完成复查的比例；用户未提供信息与系统失败分别统计 |
| 解决率 | 全部诊断案例中按预先定义的业务成功条件解决的比例；工具确认与用户反馈分别报告 |
| 转人工准确性 | 对标注的应转/不应转案例计算 Precision、Recall，并报告交接是否实际成功 |
| 性能与成本 | 同一环境下报告耗时分位数、输入/输出 Tokens、工具次数和实际费用；失败样本也计入 |

- 固定评测集、运行脚本、三组对照报告与失败案例分析。
- 成本与性能优化记录、CI 门禁、部署演示及项目介绍材料。

### 验收标准

- 保留验收集中的索引并发覆盖、活动版本误删、重复结算、越权、凭据泄露、虚构核查成功及重复建单等关键案例全部通过；明确这只代表固定测试集结果。
- 诊断与复查效果相对基线有可复核改进，未达成项保留失败记录并修复或列为明确限制。
- 性能与成本目标在测得基线后写入报告并冻结；优化不能以降低关键质量指标换取，样本不足时不声称普遍提升。
