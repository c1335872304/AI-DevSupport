# API 认证、Key 生命周期与权限手册

API Assistant OpenAPI Demo 使用 API Key 识别应用。本文只描述通用认证事实；某个客户当前 Key 是否有效，必须通过 `query_api_key_status` 查询实时业务数据。客服、知识库和模型都不得从 Key 字符串本身推断客户状态。

## 1. 认证请求规范

服务端请求应在安全的服务端进程中携带 API Key。前端浏览器、公开仓库、截图、日志和客服对话中不得出现完整 Key。应用应：

- 使用 HTTPS；
- 从密钥管理或运行时环境读取 Key；
- 为不同应用、环境和用途使用不同 Key；
- 对失败响应记录 `request_id`，但不记录 `Authorization` 原文；
- 轮换后逐步切流，并保留可撤销的旧 Key 过渡窗口。

## 2. 认证错误码

### AUTH_KEY_EXPIRED

表示调用使用的 API Key 已经过有效期。客服应先用调用日志确认 `app_id` 和错误码，再用 `query_api_key_status` 查询实时状态。修复方式是创建或轮换有效 Key，更新服务端配置，并用低风险请求验证。不能通过重复重试让过期 Key 恢复。

### AUTH_KEY_INVALID

表示 Key 无效、格式错误、已禁用，或不属于当前应用。应检查应用与 Key 的对应关系、环境变量和部署版本。不要从旧日志推断当前状态，也不要要求客户把完整 Key 发给客服。

### AUTH_KEY_DISABLED

表示 Key 被主动停用或因安全策略被冻结。需要确认是否存在泄露、违规或组织策略变化；恢复或重新创建属于受控业务操作，必要时转人工。

### 401 与 403 的区别

`401` 说明认证凭据无法被接受，常见是缺失、过期或无效；`403` 说明身份已经识别，但当前身份没有访问资源的权限。两者都不能仅凭 RAG 判断客户的实际权限，必须结合日志和权限 Tool。

## 3. Key 轮换流程

1. 确认受影响的应用、环境和调用时间；
2. 用 `query_call_log` 查询最近失败请求的 `app_id`、endpoint、状态码和错误码；
3. 用 `query_api_key_status` 检查 Key 的 ACTIVE、EXPIRED、DISABLED 状态；
4. 如果怀疑泄露，立即停用旧 Key，创建新 Key，并检查异常调用；
5. 将新 Key 写入服务端密钥配置，不要提交到代码仓库；
6. 用低风险、可观测请求验证新 Key；
7. 观察一段时间后撤销旧 Key，并记录变更时间和操作者。

## 4. 客服可以和不能做什么

客服可以解释错误码、要求脱敏信息、指导轮换步骤，并查询经过权限校验的状态。客服不能：

- 要求客户粘贴完整 API Key、密码或 Access Token；
- 在聊天中回显完整凭据；
- 仅凭 RAG 断言某个客户的 Key 当前有效；
- 直接修改、恢复或删除客户 Key，除非有明确授权的业务 Tool；
- 把 403 错误错误地解释成 Key 过期。

## 5. 证据要求

回答具体认证问题时，至少需要 `request_id` 或 `app_id`、HTTP 状态码、错误码和调用时间。若日志不存在、Key 状态查询失败、多个证据冲突，应该说明无法确认并转人工，而不是给出确定性账户结论。知识库只能作为通用规则来源；个人状态必须来自当前用户可访问的 API Tool。
