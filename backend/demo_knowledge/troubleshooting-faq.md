# API 故障排查运行手册

本文档把常见客服问题整理为可执行的排障 Runbook。每一步都要记录使用了什么 Tool、得到了什么证据和还缺什么信息；不能用知识库中的通用规则代替客户实时状态。

## 1. 统一入口

先判断问题属于认证、限流、超时、服务端错误、账单/退款还是权限问题。收集 `request_id`、发生时间和时区、endpoint、HTTP 方法、状态码、错误码、应用标识和重试情况。禁止要求客户发送完整 API Key、密码或支付信息。

## 2. 401 认证故障

1. 用 `query_call_log` 查询 `request_id` 对应的 `app_id`、endpoint、HTTP 状态和错误码；
2. 用 `query_api_key_status` 查询当前 Key 的状态；
3. 用 `query_error_code` 解释 `AUTH_KEY_EXPIRED`、`AUTH_KEY_INVALID` 或禁用状态；
4. 指导客户轮换 Key 并用低风险请求验证；
5. 如果日志和 Key 状态冲突，保留冲突证据并转人工。

不要把 401 解释成网络超时，也不要在没有 `query_api_key_status` 结果时断言“你的 Key 一定有效/无效”。

## 3. 429 限流故障

1. 确认错误码是否为 `RATE_LIMIT_EXCEEDED`；
2. 用 `query_plan` 查询 QPS 和月额度；
3. 用 `query_recent_call_stats` 查询窗口内请求数、429 数和限流比例；
4. 建议指数退避、jitter、降低并发和批量大小；
5. 如果客户要求提高限额，进入套餐或人工流程。

429 不一定意味着月度额度耗尽。只有套餐、用量和近期统计一致时，才能说明可能的原因；无法确认时应诚实说明。

## 4. 超时与无日志

先确认是单个 endpoint、单个区域还是全部请求超时，并记录客户端超时时间和重试次数。若有 `request_id`：

- 日志显示服务端已完成：不要重复执行有副作用的写操作，先读取结果；
- 日志显示服务端失败：结合错误码和时间分析；
- 完全没有日志：检查 DNS、代理、网络、连接池和请求是否真正发出；
- 证据不足：不要把故障归因给服务端或客户网络，转人工。

## 5. 5xx、未知错误和部分失败

收集状态码、错误码、`request_id`、时间和受影响 endpoint。对幂等读取可以有限退避重试，对创建、扣费、退款等写操作必须确认幂等键和上一请求状态。多个 Tool 部分成功时，答复只能使用成功事实，并列出未解决项目，不得把失败说成恢复。

## 6. 停止自动排障条件

出现以下任一条件应进入人工决策：

- 客户明确要求人工；
- 已按建议重复排查仍未解决；
- 涉及退款、改价、套餐变更或其他高风险写操作；
- Tool 超时、不可用或返回相互冲突的结果；
- 需要内部生产日志、审批或权限才能继续；
- 客户状态可能受到安全事件影响。

人工转接必须发生在事实收集和证据汇总之后。只有工单 Tool 成功返回 `handoffId`，最终答复才可以确认工单已经创建。

## 7. 知识库与业务 Tool 冲突

通用政策来自 RAG，实时客户事实来自权限校验的业务 Tool/MCP。两者冲突时，不要选择一个结果强行回答；应向客户说明正在核验、列出已确认事实和待确认事实，并转人工。
